LCLS-II timing frame
====================

The LCLS-II timing system sends one frame per fiducial on a serial link. The
transceiver delivers it to the receiver as one 16-bit symbol per clock, each
symbol with two K flags. This page describes the frame as the regression's
reference model encodes it, :repo:`tests/common/timing_model.py`, which the
production receivers decode in simulation. The diagrams are generated by running
the model's encoder, so a change to the model changes them on the next
generation.

Symbols and K characters
------------------------

A symbol is ``data`` (16 bits, high byte then low byte) and ``dataK`` (2 bits, the
K flag of the high byte then of the low byte). The framing symbols all carry the
data character D21.5 (``0xB5``) in the high byte and a K character in the low byte:

.. list-table::
   :header-rows: 1
   :widths: 20 15 15 50

   * - Symbol
     - data
     - dataK
     - Use
   * - idle comma
     - ``0xB5BC``
     - ``01``
     - K28.5, sent between frames.
   * - alignment comma
     - ``0xB53C``
     - ``01``
     - K28.1, sent once before the start of frame.
   * - SOF
     - ``0xB5F7``
     - ``01``
     - K23.7, start of frame.
   * - EOS
     - ``0xB51C``
     - ``01``
     - K28.0, end of segment.
   * - EOF
     - ``0xB5FD``
     - ``01``
     - K29.7, end of frame.

The values come from the constants of ``TimingPkg`` and are the model's
``IDLE_SYMBOL``, ``ALIGN_SYMBOL``, ``SOF_SYMBOL``, ``EOS_SYMBOL``, and
``EOF_SYMBOL``.

Frame structure
---------------

A frame is the alignment comma, SOF, one or more segments, EOF, and two CRC
words. A segment is a start-of-segment word (SOS), its data words, and EOS. The
SOS word is ``(stream_id << 12) | (last << 7) | offset``, with ``dataK`` ``00``:
the stream id is 4 bits, ``last`` is 1 for the last segment of a stream, and the
offset is 7 bits. Stream 0 carries the timing message, so a frame of one message
is one segment of 59 words (see :doc:`timing_message`).

.. include:: ../_generated/lcls2_frame.inc

The CRC is a CRC-32 (polynomial ``0x04C11DB7``, reflected) over the SOS words,
the data words, the EOS words, and the EOF word. It does not cover the commas or
SOF. The serializer sends the byte swap of the standard CRC-32, low 16 bits
first, so the two CRC words follow EOF in that order. ``TimingDeserializer``
(:repo:`LCLS-II/core/rtl/TimingDeserializer.vhd`) recomputes the CRC while it
sorts the words into streams and raises ``crcErr`` when it differs from the CRC
words received.

Segments and extension streams
------------------------------

A frame may carry segments for stream ids 0 to 15.
``TimingFrameRx`` (:repo:`LCLS-II/core/rtl/TimingFrameRx.vhd`) turns stream 0
into the timing message and streams 1 to 15 into extension messages of up to
32 words (512 bits) each, delivered as ``TimingExtensionMessageType``. A shorter
extension segment is shifted into the end of its 32-word register, so its word 0
sits at word index ``32 - n`` for a segment of ``n`` words and the words below it
are stale (measured in :repo:`tests/lcls2_core/test_TimingFrameRx.py`; the
extension outputs are not latched on the strobe, a question in :issue:`211`).
The default extension layout is described on :doc:`extension_package`.

The strobe for a frame arrives when the start of the next frame is seen, so the
receiver delivers the previous frame.

Two layouts that are not the 944-bit message appear on the same link or in the
same package. The 672-bit variant, produced by ``toSlvNoBsa`` for the EVR pulse
generator, drops the version and the four BSA masks and moves ``control(16)`` into
the word where ``syncStatus``, ``mpsValid``, and ``bcsFault`` sit in the full
message; the model calls that word ``modifier``. The 320-bit ``ExptMessageType``
is the default extension message on stream 2.

Checks the receiver makes, and those it does not
-------------------------------------------------

``TimingFrameRx`` compares the version of each message with
``TIMING_MESSAGE_VERSION_C`` (``0x0001``). A different version sets bit 4 of
``staData`` and holds ``timingMessageValid`` low from the cycle after the strobe.
It latches the version into ``rxVersion``.

The measured behaviors below are observed in simulation; the intent of the
maintainers is not confirmed, and the questions are open as :issue:`211`:

- A frame with a wrong CRC sets ``staData`` bit 3 once and is still delivered,
  with ``timingMessageValid`` high.
- The receiver has no length check. A 58-word stream 0 segment leaves the previous
  frame's last word at index 0, so every field is shifted up by one word, and a
  60-word segment loses its first word. Both pass the CRC.
- ``TimingDeserializer`` tests ``dataK`` only for EOS and EOF. A K character
  written over a data word inside a segment is delivered as data and counted in
  the CRC.
- The 672-bit decode in ``toTimingMessageType`` leaves ``version``,
  ``syncStatus``, ``mpsValid``, ``bcsFault``, and the BSA fields unassigned.

The regression decodes model-encoded frames with the unmodified
``TimingFrameRx`` and ``TimingDeserializer``; the 944, 704, 416, and 320-bit
walks that fix the message layouts agree with ``TimingPkg`` bit for bit
(:repo:`tests/lcls2_core/test_TimingPkgConversions.py`).
